# Acceptance — текущая ревизия

Классы статусов: **automated PASS** — исполненный unit/integration test; **live PASS** — реальная LLM и браузер, не scripted provider; **expected safe BLOCK** — намеренная остановка; **UNVERIFIED** — не исполнено или нет условий. Наличие tool в registry само по себе не означает прохождение бизнес-сценария.

## Финальная desktop acceptance

Настройте LLM, выполните `--check-llm`, запустите Chrome CDP по README, войдите вручную. Начните с `CONFIRMATION_MODE=all`. Не используйте реальные платежи для демонстрации.

### Почта

1. Попросить прочитать последние 10 писем и перечислить кандидатов в спам с причинами.
   На большой виртуализированной ленте агент может использовать `extract_collection` вместо многократного полного `read_page`; это не должно менять письма.
2. До анализа и согласования список писем должен остаться неизменным.
3. Проверить соответствие выбранных сообщений реальной странице; отрицать сомнительное предложение.
4. Разрешить перемещение выбранного тестового письма; дождаться свежего списка/счётчика/папки спама.
5. Итог должен указывать реально обработанные письма, отказанные и непроверенные действия. Успех click без результата — FAIL.

### Магазин/доставка

1. Задать точные товары, варианты, количества, валюту и бюджет. На существенно неоднозначный выбор агент задаёт ask_user.
   Каталог можно исследовать через `extract_collection`; конкретные controls из extraction остаются actionable только на ближайший decision и не заменяют последующую проверку корзины.
2. Сверить карточки и цену; после добавления — конкретные строки корзины, варианты, количество и итог.
3. Дойти до оформления. Отказать оплате. Заказ не должен оплачиваться, повторно запрашиваться тем же действием или объявляться оплаченным.
4. При сетевом таймауте отправки сначала проверить состояние, не повторять транзакцию автоматически.

### Вакансии

1. Прочитать существующее резюме в браузере, сохранить ключевые подтверждённые факты.
2. Исследовать не менее трёх разных подходящих вакансий, сохранить URL/условия; сравнить с резюме. Для списка карточек допустим `extract_collection`, для сложной страницы вакансии — `extract_page`.
3. Подготовить индивидуальные письма без выдуманных навыков и опыта.
4. Перед каждой фактической отправкой — confirmation; после неё — receipt/статус отправленного отклика.
5. В итоговом отчёте различать «подготовлен», «отправлен и проверен», «запрещён» и «не проверен».

### Универсальность и handoff

Повторить простую задачу на незнакомом сайте без изменения Python/JS агента. При CAPTCHA/2FA пользователь завершает проверку в Chrome и отвечает в ask_user; агент наблюдает страницу заново. Если ручное действие недоступно — blocked с причиной. Вкладки управляются через generic `manage_tabs` (старый `switch_tab` оставлен для совместимости). На crowded pages допускается `find_in_page`; для структуры страницы — `extract_page`/`extract_collection`; для независимых полей — `fill_form`. File attachment разрешён только из `BROWSER_UPLOAD_ROOT` и после confirmation.

Записывайте backend/model, task, фактические browser actions, confirmation decisions и observed outcome. Удаляйте приватные данные из записи. Исторические прогоны из входного архива не заменяют эти проверки новой версии.

## Приёмка патча runtime hardening (текущая ревизия)

Тестовый стенд: `python -m http.server 8765 --bind 127.0.0.1 --directory tests/fixtures`, адрес `http://127.0.0.1:8765/acceptance.html`.

В Windows/CDP используйте отдельный профиль, ручную авторизацию и сначала `CONFIRMATION_MODE=all`. Для проверки автономного безопасного поиска можно использовать `risky`. Ключ и данные аккаунта остаются локально.

1. **Browser/LLM smoke:** `--check-browser`, `--check-llm`, затем полный pytest. Убедитесь, что CDP disconnect не закрыл Chrome.
2. **Wikipedia с реальной LLM:** точная задача из LIVE_E2E.md. Начало только с главной; ввод через видимое поле; никаких вручную построенных article URLs. Ожидаются наблюдаемый год 1137 и фактический source URL. Focus click не должен создавать pending; синонимы поиска ограничиваются runtime. Сохраните redacted trace и число шагов. Сетевой/CAPTCHA block — честный blocked, не PASS.
3. **Стенд MAIL:** попросите прочитать 10 сообщений, объяснить obvious spam, сохранить кандидата. До approval список неизменен. Разрешите только сообщение 7; ожидается receipt о Trash и девяти оставшихся. Повторите с отказом — удаления быть не должно.
4. **Стенд SHOP:** Hardcover, quantity 2, бюджет 30 EUR. Проверьте название/вариант/количество/unit price 12 EUR/total 24 EUR. Checkout можно подготовить; откажите оплате. Финальный результат обязан сказать, что оплаты не было.
5. **Стенд JOBS:** прочитать synthetic profile, выбрать три карточки, подготовить три разных правдивых письма. Подтвердите отдельно каждый submit; проверьте три receipts. Не считать открытие формы отправленным откликом.
6. **Upload:** создайте папку с одним фиктивным резюме, задайте BROWSER_UPLOAD_ROOT. Approval должен назвать файл без пути. После разрешения filename виден в UI; после отказа файл не выбран. Настоящее резюме для этого smoke не требуется.
7. **Form recovery:** оставьте обязательное поле пустым; агент не должен объявлять submit успешным. Исправление и multi-step continuation должны сохранять goal/ответы. Проверьте autocomplete вашего сайта отдельно — native datalist не покрывает все custom widgets.
8. **Tabs и handoff:** popup входа → ручной login → возврат. Закройте popup вручную, проверьте recovery. Откажите закрытию вкладки с черновиком. CAPTCHA/OTP выполняет человек в браузере; секреты в чат не передаются.
9. **Минимальная реальная authenticated приёмка:** read-only почта, корзина без оплаты, черновик отклика без отправки. Реальные mutations — только после просмотра и явного подтверждения. Нестандартные controls проверяйте в режиме all.

Для работодателя приложите результат именно текущего ZIP и честно отделите автоматизированный scripted suite от live LLM. Готовность к сдаче нельзя выводить только из зелёного pytest.
